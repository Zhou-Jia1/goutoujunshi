# T26 连续分析与长记录处理

本包接入已经可用的确认文字、分享与导入证据。T22 OCR SDK 选择仍待负责人确认，Q 工作区冻结；没有接入或宣称完成截图 OCR、完整 M2 或 M3。所有例子、截图、Key 字符串和 HTTP 测试均为虚构，仅访问本机 MockWebServer。

同一联系人再次导入后，网络投影按可解析时间合并消息；有偏移量的时间先换算为同一时间基准。缺失或不可解析的时间放在已知时间之后，保持当前来源顺序，不推断发生时间。连续「序号」仅是本次排序后的阅读标签；原导入及 ChatLine.id 不改写。每行仍带 canonical ID、导入 ID 和来源，事实引用使用 canonical ID，因此插入更早的消息不会让旧引用指向另一句话。完整 AnalysisRequest.evidence 始终保留，T27 恢复与 T25 原答案 authority 继续对比完整证据。

历史上下文只读取当前联系人的真实已完成 assistant、对应原 run.requestSnapshot 和主动反馈 PLAN。原来源集合必须逐个完整保留，内容、说话人、联系人和来源类型都不变；允许在集合之外新增导入，删除或修改旧来源则排除该轮。隐私与模型配置版本必须匹配。最近两轮分别提取 VERDICT、NEXT 和用户选择（SENT / PENDING 修改，未记录时明示），标为历史建议而非聊天事实；Demo 标为虚构演示。反馈仍不产生学习样本或学习授权。T25 当前答案操作继续使用更严格的原来源版本检查，未放宽其改写、反馈或来源 Modal 权限。

## 字符预算与明确步骤

- 输入 4000 码点、额外上下文 4000 码点、真实知识参考最多 3 份及 24k、总提示词 48k 码点门禁保持。
- 最近消息按 12k 预算选择完整行，计算时为原 ID、编号、来源标签和说话人预留空间；实际经过统一脱敏及 XML 转义后的证据再次检查 12k。单条最新消息无法容纳时明确失败，保留完整输入，不发送空证据。
- 最近窗口之前的消息过多时，只选可容纳的一份早期节选，至多先调用一次模型整理；更早未选部分明确标为遗漏，绝不声称整段或 1000 条都已经逐字总结。预览中 `record_scope` 给出总条数、实际选择条数、遗漏条数，原始 ID 与连续阅读序号同时展示。
- 第一步独立预览早期节选并确认。返回时间线每个非空行必须以本次所选消息的真实 ID 开头，未知引用、未确认来源、无编号或超过 1000 码点的结果拒绝；脱敏占位符可留在正文，不能充当来源。
- 第一步完成后仅保存摘要并显示「请预览并确认第二步」。第二步的完整分析带最近窗口、当前可验证的时间线与历史上下文，重新组装实际完整预览，重新确认才发送。第一步的确认不能授权不同的第二个 HTTP body，不静默继续计费。
- 历史摘要原有 2k 上限保持；有时间线时历史上限 1k、时间线上限 1k。时间线再次统一脱敏，扩展后超预算就停止准备，不截断成不可验证引用。
- Demo 使用本地虚构回答及本地预算窗口，不调用摘要模型，也不把示例回答冒充真实用户时间线。

`ContinuousAnalysis.plan(evidence, overlay = true)` 是留给未来悬浮功能的可测试规划入口，固定 `needsSummary=false`，只返回本地预算窗口。未来调用方可取用已经验证的缓存，不允许由该点击追加摘要请求；本包没有提前实现 M3 服务或悬浮权限。

## 缓存、失效与恢复

所有模型步骤复用 canonical SKILL、场景与真实 1–3 份参考，之后走同一个 Redactor / FrozenPromptAssembler / CompletionBody。第一步使用既有 typed `OutboundEngine.summarize`，不建第二套网络或知识库。真实预览和实际 HTTP 使用同一冻结结果，测试逐字比较 body。

正式摘要使用加密 OwnedRecord 的 SUMMARY kind，保留联系人 FK；写入事务检查 owner、sourceRevision、会话版本、已保存输入和隐私 revision，删除后不能重建 owner。没有 Room DDL 变化。缓存 key 包含联系人、完整来源及来源版本、持久输入版本（conversationRevision 与原输入正文）、隐私规则、配置 revision、知识版本、选择身份及其他请求内容。进程内 inputRevision 只用于操作回调，不作为跨进程缓存版本；key 中将其规范化，完整请求快照仍保留原值用于恢复。这样在摘要完成、尚未确认完整分析时重建控制器，不会重复摘要。

来源/记忆等现有失效事务清除生成缓存；隐私规则保存清除该联系人摘要；联系人删除由 FK 级联，全清沿用原清理流程。配置和知识变化因 key 不匹配不能复用旧摘要，输入及来源变化也拒绝旧结果。临时摘要仅在 Application 作用域控制器 RAM 中，没有 DB、DataStore、文件、Bundle、SavedState 或后台任务写入；离开临时会话即清除。

摘要是独立 run，不额外保存用户消息，也不保存普通 assistant 策略。完整分析才产生本轮用户与助手消息。失败手动重试沿用同一 requestId，Live 仍需实际预览确认；完成结果存储失败使用 T27 Recovery.Complete，仅修复存储，不再次调用模型。取消、输入、来源、规则、配置和联系人变化沿用原 mailbox / epoch 门禁丢弃晚结果。

摘要中的更高安全级别立即发布并写入原加密 run 检查点；CRISIS 不显示普通答案、不进入后续完整分析。摘要完成但没有普通 assistant 时，重建也读取当前来源的最高摘要安全级别；失败或存储重试不降低。请求新增投影字段均有默认值；旧 T25 / T27 canonical 指纹仅在新增字段为空且旧字段精确相等时兼容，没有放宽同 ID 操作身份检查。

UI 只组合已有 DS 组件与 tokens，文案进入 strings.xml。没有新增 DS API 或视觉令牌。截图展示独立摘要步骤、等待、完成后等待再次确认、失败及浅色/深色/平静/有效 260% 字号。

## QUALITY 反馈修复

新增三条失败时序回归先复现问题（`t26-quality-red.log`），随后定向 T26 / T27 / 原控制器通过（`t26-quality-fix-confirm.log`，21 秒）：

2. 摘要 cache 已完整保存、最终 COMPLETED 检查点失败后重建，显式恢复先核对同 requestId、实际缓存 key、来源与引用。RUNNING / INTERRUPTED 的完整结果只补完成存储，再准备新的 Full 实际预览；不再次调用摘要模型。普通新操作只复用对应真实 COMPLETED run 的 cache，不能把未完成的结果当 ready cache。
3. 取消摘要的补偿删除若抛 IO 异常，RAM 清理仍在独立 finally 中执行，同时保留进程内 blocked request 与待清理集合，阻止普通模型请求。清理可主动重试且只做存储，不联网；stop / 切换会话不会抹掉待清理状态或把错误伪装成成功。另尝试将原 run 持久标为 CANCELLED 以阻止重建后复用；摘要 CANCELLED 状态不会在恢复加载时被改写为 INTERRUPTED。旧请求的补偿仍只删除同 key、同 requestId，不能删除新请求有效结果。

如果所有存储 IO 都失败，进程终止后只能回到最后成功持久化的版本；这里没有声称物理 IO 可以保证必定写成。失败仍明确呈现存储错误，当前进程保留清理门禁供重试。全清成功后相关 RAM 门禁与缓存一并清除。
